# Public access and future authenticated RAG

[Project overview](../README.md) | [Deployment](deployment.md) | [Lifecycle](lifecycle.md)

## Implemented modes

One application and one RAG pipeline serve two implemented modes:

- `APP_MODE=development`: the existing upload, extraction, chunking, embeddings, indexing, hybrid retrieval, answers and document lifecycle API/UI. Default only when `KNOWLEDGEOPS_ENVIRONMENT=development`. Use a loopback listener and a trusted operator identity; this is not a public application mode.
- `APP_MODE=public_demo`: anonymous questions over one operator-approved six-page `employee-handbook.pdf`. No public data mutations, document selection, index selection, retrieval diagnostics, or administration.

`KNOWLEDGEOPS_ENVIRONMENT=production` requires explicit `APP_MODE=public_demo`, managed identity and exact HTTPS CORS origins, plus existing validated service configuration. Missing/invalid mode fails startup. `authenticated`, `full_rag`, or other unimplemented modes are rejected. Do not override the production environment to development in hosting configuration. Configuration is operator-controlled, never accepted from a browser.

The frontend fetches `/api/config` before showing controls, fails closed on missing/invalid capabilities, and has no independent mode switch. Configuration publishes only mode, management capability, question length, synthetic filename and suggested questions. The backend always enforces policy even if a visitor edits frontend JavaScript.

## API access matrix

| Operation | Anonymous public demo | Trusted development | Future authenticated application |
| --- | --- | --- | --- |
| `GET /health` | Minimal process health, no Azure checks | Same | Same |
| `GET /api/config` | Non-sensitive capabilities | Development capabilities | Requires future implementation |
| `POST /api/answers` | Approved handbook only; usage limits | Existing shared-corpus flow | User-authorized scope and quotas required |
| `POST /api/retrieval` | Blocked | Existing debugging endpoint | Decide exposure and authorized scope |
| `POST /api/documents` | Blocked before multipart parsing | Existing ingestion/duplicate detection | Ownership, upload quotas required |
| `GET /api/documents` | Blocked | Existing catalog/listing | Owner-filtered listing required |
| `DELETE /api/documents/{document_id}` | Blocked before dependencies | Existing lifecycle deletion | Owner authorization required |
| `/docs`, `/redoc`, `/openapi.json` | Disabled and blocked | Available | Restrict deliberately |
| Other/new routes and methods | Blocked by default | Normal FastAPI behavior | Explicit policy required |

Only exact GET health/config and POST answers are allowlisted. Matching CORS OPTIONS preflights are permitted. Other methods, trailing-slash variants, query parameters, and unknown routes receive 403/422 before their handlers. A public JSON request may contain only `question`; `top_k`, document/index selectors, filters, and duplicate JSON keys are rejected. CORS grants no authorization.

Maintenance/index-creation/evaluation scripts are CLI tools, not HTTP routes. They require a trusted operator shell/identity. The production image excludes scripts and evaluation artifacts; do not mount operator credentials or expose a terminal. Production Search permissions are read-only.

## Corpus boundary

No new index is required or created. The server uses its configured normal Search index and a mandatory `DEMO_DOCUMENT_ID` UUID. Filename alone is never an authorization boundary. Each query enumerates only that UUID's metadata, requires six distinct chunks with filename `employee-handbook.pdf`, pages 1-6 and chunk indices 0-5, then applies:

```text
document_id eq '<server-approved UUID>' and filename eq 'employee-handbook.pdf'
```

This filter is applied to the hybrid query with `vector_filter_mode=preFilter`, qualifying keyword and vector evidence. See [Azure vector filters](https://learn.microsoft.com/en-us/azure/search/vector-search-filters). Returned IDs, filename, page/index and chunk keys are checked against the enumerated manifest before evidence reaches generation. Missing/incomplete/mismatched data causes a safe 503; no unfiltered fallback occurs. Empty results within a valid corpus retain the existing insufficient-evidence behavior.

Generation still receives only the existing selected passages, uses the unchanged grounding prompt, and validates model-selected source IDs. Public responses expose filename and page only, never document/chunk/source IDs, Search scores, vectors or service endpoints. The filename/page values come from trusted retrieval metadata. They are not generated by GPT.

`knowledgeops-eval-chunks` is explicitly rejected in demo configuration. No evaluation resources are modified. Operators must verify the approved UUID/PDF and stop modifying that document while the demo is running. The adapter prevents cross-document retrieval; it does not cryptographically attest that a privileged operator has not overwritten content under the approved UUID. `/health` is process liveness, not corpus readiness. A manual answer check is required before advertising access.

A dedicated third demo index would further reduce the data accessible to a compromised runtime identity, but consumes the remaining Free-tier index slot. It is optional and requires explicit approval before creation. After approval, use the existing `scripts/ensure_search_index.py` with the new operator-configured index, then the existing trusted development upload pipeline. Record the new UUID and verify its six chunks before changing demo settings. Never recreate/delete an existing index, and never reuse the evaluation index. Shared-index document filtering remains required even with a dedicated index. No provisioning command was run for this implementation.

## Usage controls and limitations

| Setting | Default | Effect |
| --- | ---: | --- |
| `DEMO_REQUESTS_PER_MINUTE` | 5 | Rolling 60-second limit per actual socket peer |
| `DEMO_GLOBAL_REQUESTS_PER_MINUTE` | 20 | Rolling 60-second total answer admissions |
| `DEMO_GLOBAL_REQUESTS_PER_DAY` | 100 | Rolling 24-hour total answer admissions |
| `DEMO_MAX_CONCURRENCY` | 1 | Active answer workers, configurable up to 2 |
| `DEMO_MAX_QUESTION_CHARS` | 500 | Strict question limit, configurable up to 1000 |
| `DEMO_MAX_BODY_BYTES` | 8192 | Raw JSON bytes, including streamed bodies, before parsing |
| `DEMO_TOP_K` | 5 | Server-controlled results, maximum 5 |
| `DEMO_MAX_COMPLETION_TOKENS` | 2048 | GPT completion/reasoning budget; maximum 4096 |
| `DEMO_REQUEST_TIMEOUT_SECONDS` | 45 | Maximum wait for the complete answer |
| `DEMO_BODY_TIMEOUT_SECONDS` | 5 | Maximum wait to receive a question body |
| `DEMO_AZURE_TIMEOUT_SECONDS` | 15 | Embedding/generation and Search transport timeouts |
| `DEMO_AZURE_MAX_RETRIES` | 0 | Azure Search/model SDK retries; maximum 1 |

Admission counts include malformed questions and failed/busy requests, preventing free retry floods. Rate and concurrency denials return 429 with Retry-After; overload does not queue more AI work. Oversized bodies return 413, invalid questions/selectors 422, slow bodies 408, answer timeouts 504, provider failures 502/503. Compressed bodies are rejected. Errors do not include Azure SDK bodies or credentials. No document/question text is logged by these controls.

A response timeout cannot forcibly interrupt synchronous SDK calls. The worker remains counted until it finishes, so repeated timeouts cannot create unlimited overlapping model requests. Underlying network/identity retries and credential acquisition may outlast the HTTP deadline; the demo stays busy rather than freeing the slot early. An abandoned browser request may still incur AI usage. No automatic application retry occurs. SDK retries are bounded separately.

The limiter is in memory, one event loop, one process. Restarts reset it; workers/replicas each have independent counters. Revision overlap can briefly multiply budgets. Keep one Uvicorn worker, one replica maximum, Single revision mode, no revision traffic splitting, and drain/stop the old revision during upgrades. The visitor map is bounded to 2,000 active peers and fails closed when full. Distributed-IP abuse and denial of service remain possible. Health/config requests have no AI cost and no application rate limit. This is not DDoS protection or a hard spending cap.

### Proxy identity

Run Uvicorn with `--no-proxy-headers`; never use `--forwarded-allow-ips=*`. The application ignores `X-Forwarded-For`, `Forwarded` and similar headers for visitor identity. Behind Container Apps, visitors may share the same ingress socket peer and therefore one conservative shared visitor limit. This limits usability but prevents a visitor from bypassing limits by inventing IP headers.

[Container Apps documents only its rightmost X-Forwarded-For entry as platform-provided](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview). Before implementing trusted proxy parsing, verify actual ingress behavior, proxy peer ranges, appended header semantics, duplicate headers, ingress-only reachability and spoofing tests. No trusted-forwarded-IP parser is enabled now. Do not loosen the safe fallback merely to improve demos.

## Future authenticated public RAG: design only

This mode is not implemented or selectable. Before enabling it:

1. Choose an identity provider. Microsoft Entra External ID fits external users; workforce Entra fits an organization-only app. Compare provider cost, Free Trial availability and supported account types before selection. Use a maintained provider rather than building password storage. No provider/resource is provisioned here.
2. Validate bearer tokens in FastAPI using the provider's discovery/JWKS, trusted issuer, audience, signing algorithm, signature and lifetime. Never use decoded but unverified claims or a browser-supplied user ID. Design key rotation, revoked/session handling, and 401/403 tests.
3. Create a small authorization context at the API boundary from verified issuer/subject and document permissions. Replace the demo scope adapter with an owner-authorized scope built server-side; retain the existing retrieval/generation services. Keep a distinct public handbook scope if desired.
4. Add durable document ownership and quota state (PostgreSQL is already planned). Migrate lifecycle catalog records explicitly; do not assign existing shared documents to whichever user logs in first. Duplicate hashes must respect owner/visibility boundaries and must not reveal another user's filenames or existence.
5. Namespace originals by stable internal owner ID and document UUID in private Blob Storage. Namespace/catalog ownership must cover upload, listing, deletion, retry and legacy adoption. Backend identity alone accesses storage; no public container or long-lived SAS. Any future download route must authorize ownership before streaming.
6. Migrate Search schema to include filterable owner/tenant/visibility identifiers and backfill/reindex deliberately. Every keyword/vector query must enforce authorized ownership before retrieval, then validate results and citations. Restrict listing/deletion enumeration and chunk removal by owner plus UUID; knowing a document UUID grants no access. Test cross-user filters, indirect object references and malicious selectors.
7. Reserve and enforce per-user upload bytes/page/chunk/storage limits and AI request/token/concurrency quotas before external calls. Use durable atomic accounting for multiple replicas and reconcile uncertain provider outcomes. Avoid allocating resources before authorization. Document retry/idempotency behavior.
8. Add abuse controls, token/cost monitoring without sensitive prompts, retention policy, user deletion and eventual Blob soft-delete/version cleanup policy. Alert on quota use and leaks, but do not treat alerts as a payment cap.
9. Add backend/frontend integration tests for two unrelated users, shared documents if supported, revoked/invalid tokens, owner-isolated citations, quotas and all lifecycle failures. Preserve historical evaluation baselines; add independent security tests rather than changing scoring.

Only after ownership migration, authorization enforcement, quota checks and hosted verification should a new authenticated mode be added to the allowlist. Reuse the current ingestion/retrieval/answer orchestration; do not fork a second RAG implementation.
